# 开发计划索引

本目录用于长期记录 OpenPINN 的开发阶段、任务状态、验收证据和重要决策。计划文档是执行记录，
理论定义仍以 [`../../tutorials`](../../tutorials) 下的推导文档为准；项目模块边界以各项目 README
为准。

## 编号规则

计划文件采用三位连续编号：

```text
NNN-short-topic.md
```

- `NNN`：仓库范围内递增的计划编号，从 `001` 开始，编号一经使用不回收；
- `short-topic`：简短、稳定的英文主题，避免将日期或临时状态写入文件名；
- 一个计划对应一个具有独立验收门槛的开发阶段；
- 范围发生根本变化时新建计划，不覆盖旧计划；
- 小范围调整直接记录在原计划的“变更记录”中。

计划内部使用以下标识：

- `NNN-Txx`：开发任务；
- `NNN-Axx`：阶段验收项；
- `NNN-Dxx`：需要固化的设计决策；
- `NNN-Rxx`：已识别风险。

## 状态约定

| 状态 | 含义 |
| --- | --- |
| `待开始` | 范围已明确，但尚未实施 |
| `进行中` | 已开始实施，尚未满足完成条件 |
| `阻塞` | 存在明确外部依赖或待决问题 |
| `待验收` | 实现已完成，正在收集验收证据 |
| `已完成` | 所有阶段验收项均已通过 |
| `已取消` | 任务不再实施，并已记录原因 |

复选框只表示任务动作是否完成；计划整体状态必须由验收项决定。测试失败时不得通过放宽容差、删除
样例或更改理论定义来直接关闭任务，除非相应变更经过明确评审并记录。

## 开发与实验约定

核心积累可信能力，实验积累有边界的证据，基线积累可复现的成功案例。三者相互支持，但不使用
同一个“完成”标准。以下约定用于组织后续任务与验收，不追溯更改已有计划状态或降低验收门槛。

### 1. 理论、核心与实验的职责

理论文档保持理论性，负责模型假设、控制方程、变分关系和适用范围；开发计划负责实现选择、
状态管理、验收证据和决策记录。实验中的新模型假设必须明确写出依据，不能用训练结果静默改写理论。

核心提供假设明确、行为可验证、失败可识别的物理与数值组件。核心不仅包括经典物理公式，也包括
稳定的积分、场传递、求解流程、状态回滚和诊断；物理实现应符合理论，数值组件应满足明确的接口
与算法契约。“经典方法”不意味着适用于所有场景，也不能代替实现验证。

核心保证按约定求解和检查结果，不保证任何网络、参数或载荷下都能收敛。超预算、违反约束或未收敛
时，应报告失败，且不得提交不合格状态；如实失败也是基础设施的正确行为。实验依赖核心，核心不得
依赖实验代码、实验配置或某次实验的隐式输入。

### 2. 分开记录组件、实验与基线验收

| 对象 | 完成或通过的依据 | 不能据此宣称 |
| --- | --- | --- |
| 核心组件 | 公式、接口与失败语义通过对应测试和局部基准 | 完整裂纹扩展已经算准 |
| 开放实验 | 按预先声明的范围完成比较，保留证据并给出有边界的结论；结果可以是否定或证据不足 | 候选方法已成为可靠基线 |
| 完整基线 | 指定问题的场量、反力、能量、约束与收敛性达到冻结的验收要求 | 对未验证的模型、参数或载荷同样有效 |

同一计划同时包含三类工作时，应分别列出任务、验收项和证据。例如，二维状态回滚通过故障注入
测试后，该组件可以通过验收；扩展训练不收敛时，完整基线仍未通过，不能反向抹去已验证的组件能力。

实验结论与执行状态分别记录：按约定完成的实验可以得到否定结论；因实现错误或预算不足而终止的
实验，不能据此宣称假设被否证。计划整体仍须满足其原定全部验收项。包含成功基线要求的计划，不能
仅因失败实验已记录就标记为完成；范围根本变化时按编号规则另立计划，不改写旧目标。

### 3. 区分求解方法实验与模型对照实验

- **求解方法实验**：保持连续模型、边界和目标演化问题一致，比较网络表示、积分、优化或求解策略。
- **模型对照实验**：改变能量分解、退化函数、不可逆处理或其他数学假设；必须声明新旧定义与适用范围，
	不能把效果全部归因于训练改进。

即使都称为“历史场法”，是否累积未收敛内迭代的驱动力过冲，也可能影响最终演化。历史更新、相场
下界和状态提交时机等算法差异，应具名记录、独立测试并随结果保存；比较前声明差异，统一前经过
设计决策，不静默替换已有行为。每个实验应事先明确假设、自变量、控制量、指标、否证判据、随机性
与停止条件；存在多因素交互时，应明确对照设计，而不是同时改动后将结果归因于单一因素。

### 4. 晋升核心不等于成为默认方案

候选方案分别回答三个问题：实现是否可信，是否值得复用，是否适合作为当前基线默认值。

实现通过适用范围内的独立验证、具有实际复用需求后，可以提炼接口、补齐测试与文档，晋升为核心
可选组件；不要求它在所有问题上优于其他方法。成为默认方案则还需对应基线的比较、回归和复现证据，
并记录适用范围与代价。一次参数扫描得到的网络宽度等设置通常只进入配置，不必新增核心抽象。

扩展接口随真实实验需求逐步提炼，不提前搭建庞大的插件体系，也不把临时实验实现直接复制进核心。

### 5. 保留失败证据并限制结论

实验结果应区分没有改善、求解不收敛、实现错误和证据不足。结论应限定于已测试的模型、参数、
随机种子与计算预算。例如，加密积分后没有观察到改善，不能直接推断积分误差不重要；收益可能被
表示或优化误差掩盖。未达到实验前冻结的判据时，不得事后放宽标准以得到成功结论。

每次实验至少保存假设、完整配置、代码版本或可恢复的工作区差异、环境与随机种子、指标、停止原因、
结论适用范围和下一步决策。被否证的临时实现可以退出主代码，但应保留重建关键结果的途径；不能
只留一句“方案无效”，也不能只保留成功种子的结果。

### 6. 独立参考实现是明确的例外

生产核心中的物理公式应集中实现，普通实验和入口应复用核心，避免公式漂移。但用于交叉核验的
独立参考求解器，可以独立实现被验证的公式与离散方法，并明确参考角色、理论来源和验证范围。
若参考与被测实现调用同一个关键公式函数，就不能把它们结果一致当作该公式实现正确的独立证据。

参考实现应与生产求解路径隔离，保留自身解析测试、收敛证据和重建方式；不得成为核心的隐式依赖，
也不能仅因使用不同求解库就视为正确。具体模块位置仍遵循项目 README，不为此增加不必要的架构层。

## 维护流程

1. 开始工作前，将对应任务和计划状态更新为 `进行中`。
2. 实施中记录与原假设不一致的发现，不用代码行为反向覆盖理论。
3. 完成任务后附上测试名称、命令或结果文件等证据。
4. 所有验收项通过后，才将计划标记为 `已完成`。
5. 后续工作新建递增编号的计划，并在索引中声明前置计划。
6. 已完成计划原则上只补充勘误，不重写历史结论。
